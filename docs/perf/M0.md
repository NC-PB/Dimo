# Performance M0

Measured 2026-10-09 for the M0 exit criterion: a 50 sheet A0 PDF opens and pans smoothly
(NFR-PERF-01 first sheet under 2 s, NFR-PERF-02 60 fps with 500 balloons, NFR-PERF-03 under 1.5 GB).

## Result

| NFR | Target | Owner's Mac (M2) | Windows reference laptop |
|---|---|---|---|
| NFR-PERF-01 | First sheet visible in under 2 s | **0.82 s** (read, hash, parse 0.21 s, then 12 tiles 0.61 s). Missed before the fix below: 2.56 s | to measure |
| NFR-PERF-02 | 60 fps with 500 balloons | **60 fps held** in the app (mean 16.67 ms, p95 18 ms, max 22 ms and 32 ms). Tile side: late frames under a fast pan, see "Pan". Since T1.11 (page cache): max 18 ms at 100 percent, see "Page cache (T1.11)" | to measure |
| NFR-PERF-03 | Under 1.5 GB | **0.22 GB** peak in the Rust process, **about 0.57 GB** with the WebKit processes | to measure |

Verdict for the exit criterion on the Mac: met, with one weakness (tile throughput under a fast pan
on very dense sheets) and one gap (webview memory while scrolling through all sheets was sampled at
one sheet only). Both are in "Findings" with a proposal.

## Machine

Apple M2, 8 cores (4 performance, 4 efficiency), 16 GiB, macOS 27.0.1, Rust 1.99.0, PDFium
chromium/7881 (`scripts/pdfium.toml`), release build for the harness, debug build for `tauri dev`.
The Mac was shared with other build and test jobs while measuring (load average 6 to 10 on 8 cores).
Four harness runs agreed within about 10 percent (the worst case scroll times varied more, 2.5 to
4.0 s), but treat all numbers as an upper bound for an idle machine.

Windows reference laptop: **to measure.** Run `scripts/perf.sh` in Git Bash (needs `jq`) or call
the pieces by hand, see "Reproduce". The resident set size sampler uses `tasklist` there and has
not been run on Windows yet.

## Method

**Test document.** `dimo-synth --stress` writes a deterministic 50 sheet PDF (seed 1, 30.8 MiB,
Flate compressed) to `target/perf/`, never committed. Every sheet is A0 landscape (3370 x 2384
units) with about 40 000 line segments in chains, 3 600 circles (Bezier curves), 1 500 dimension
lines with filled arrow heads, 5 400 free text objects (a quarter rotated) and a title block:
roughly 23 000 page objects per sheet (40 000 line segments and 14 400 curve segments). Real
drawings are less uniform, so this is a stress document, not a typical one.

**Harness.** `crates/dimo-pdf/examples/perf.rs` drives the real `TileService` (default settings,
no disk cache, so everything is a cold render) with a window model of 1600 x 1000 device pixels. Tile
levels and the one tile prefetch margin follow `tiles.ts` and `Viewport.svelte`. Phases: open,
first sheet, single tile latency, scripted pan in real time at 60 steps per second, then every
sheet in turn (fit view and one detail view each) while the resident set size is sampled every
50 ms. `scripts/perf.sh` adds `/usr/bin/time -l` (peak resident set size and peak memory
footprint of the whole process), the machine description and writes `summary.json` and
`summary.md`.

**Frame times.** The webview cannot be driven from a headless harness, so NFR-PERF-02 uses the
dev hooks of T0.8 in `tauri dev` (debug build, so slower than a release build): the app opens the
document, places 500 balloons and runs the scripted pan (two circles of 200 CSS pixels in 5 s,
`pan-check.ts`) while recording the time between animation frames. The webview caps at 60 Hz, so
16.67 ms is the best possible mean.

## Findings

1. **NFR-PERF-01 was missed and is fixed.** The first run took 2.56 s: `Document` opening read
   the size of every sheet by loading each page, and loading a page makes PDFium parse its whole
   content stream (39 ms per dense A0 sheet, 1.97 s for 50). `sheet_sizes` in
   `crates/dimo-pdf/src/engine.rs` now uses `FPDF_GetPageSizeByIndexF`, which reads only the page
   boxes and rotation. Open dropped from 1971 ms to 199 ms, the first sheet from 2560 ms to
   817 ms. All `dimo-pdf` tests still pass (they cover sheet sizes, rotation and fractional
   sizes).

2. **Weakness: tile throughput on dense sheets.** The render thread loads the page for every tile
   (`render` in `engine.rs`). A spike on sheet 4 measured 52 ms to load the page and 7.5 ms to
   render a 576 px tile of it once loaded. So about 85 percent of the 38 ms per tile is
   re-parsing the same content stream. PDFium renders one tile at a time, so the pipeline
   delivers about 26 tiles per second, and a fast pan (about 19 tiles per second needed at
   32 px per frame) is close to the limit, which explains the late frames.
   **Proposal (before M1 viewer work, small):** keep the most recently used loaded page on the
   render thread (one to four pages, dropped before their document closes) and process queued
   tile requests of the same sheet back to back. Expected result: 8 to 10 ms per tile, over
   100 tiles per second. Optional second step: a prefetch margin biased in the direction of
   travel. Not done in T0.9 because it changes the render thread design; the harness reruns in
   two minutes to confirm the gain. **Done in T1.11**, see "Page cache (T1.11)" below: 9 to
   17 ms per tile.

3. **Limits of this measurement.** The stress document is uniform and synthetic, the machine was
   shared, the app frame times come from a debug build and the webview memory was sampled at two
   views only. None of these changes the verdict, but the numbers are not a guarantee for every
   real drawing: a scanned A0 sheet (raster, 300 dpi, M4 pipeline) has other costs.

## Page cache (T1.11)

Measured 2026-10-09, same machine, same stress PDF. The render thread now keeps the four most
recently used loaded pages of every open document (`crates/dimo-pdf/src/page_cache.rs`) and serves
renders, text runs and sheet analysis from them. Closing a document closes its pages first.

**Harness.** The machine was busy with other builds (load average 8 to 14), so the old binary
(before) and the new one (after) ran back to back under the same load. The third column is a
second run of the new binary at a slightly lower load.

| Measure | Before | After | After, second run |
|---|---|---|---|
| Open (read, hash, parse) | 284 ms | 330 ms | 246 ms |
| First sheet visible (open + 12 tiles) | 1086 ms | 931 ms | 517 ms |
| Tile latency, one at a time, 100 percent | mean 42.6 ms, p95 48.7 ms | mean 16.7 ms, p95 29.0 ms | mean 9.0 ms, p95 10.6 ms |
| Fast pan: frames with a visible tile missing | 42 of 440, longest run 25 frames | 7 of 440, longest run 7 frames | 4 of 440, longest run 4 frames |
| Fast pan: tile latency | p50 121 ms, p95 447 ms, max 619 ms | p50 32 ms, p95 116 ms, max 187 ms | p50 21 ms, p95 77 ms, max 104 ms |
| Scroll through 50 sheets, detail view | p50 1406 ms, max 2574 ms | p50 286 ms, max 592 ms | p50 284 ms, max 346 ms |
| Whole scroll run (2219 tile renders) | 109 s | 31 s | 27 s |
| Peak resident set size of the process | 254 MiB | 320 MiB | 282 MiB |
| Peak memory footprint (macOS) | 273 MiB | 340 MiB | 290 MiB |

The per tile cost dropped from about 40 ms to 9 ms on an idle enough machine, as predicted in
finding 2. The remaining missing tile frames of the harness come from the first tiles of a pan
over a sheet whose page is not loaded yet (one page load, about 45 ms) and from the queue of 2 to
4 workers feeding one render thread; the app shows the backdrop layer there.

**Frame times in the app** (`tauri dev`, debug build, `DIMO_DEV_BALLOONS=500`,
`DIMO_DEV_SHEET=3 DIMO_DEV_VIEW=100@1700,1200`, 992 x 682 CSS pixels at 2x, scripted pan with tiles
loading during the first lap):

| | Frames | Mean | p95 | Max |
|---|---|---|---|---|
| Before (T0.9) | 291 | 16.67 ms | 18.00 ms | 32.00 ms |
| After (T1.11) | 290 | 16.67 ms | 18.00 ms | **18.00 ms** |

No frame took longer than two frame times (33.3 ms): the T1.11 acceptance is met.

**Memory per cached page.** A spike loaded sheets 0 to 9 one after the other (one 512 px tile
each, at zoom 1 and 2) and read the resident set size after each: every dense A0 page adds about
10.5 MiB (63, 74, 85, 95 MiB for the first four), then the size stays flat at about 100 MiB
because older pages are evicted. Four pages per document cost about 42 MiB. The app after the pan
at 100 percent: app 163 MiB, WebKit GPU 178 MiB, WebContent 189 MiB, Networking 17 MiB, total
547 MiB, about the same as before (566 MiB) and far below 1.5 GB (NFR-PERF-03). The higher peak of
the harness (about 30 to 70 MiB) is the cached pages plus allocator retention; the tile cache stays
at its 128 MiB budget.

**Why four.** The tiles of one view all come from one sheet, so one page covers panning and
zooming; four keep switching between a drawing and a few detail sheets free of reloads, at about
42 MiB per dense document. The cap is per document, so several open documents add up (ten open
dense documents: about 420 MiB).

**Open risk.** The stress PDF is vector only. A cached page of a scanned sheet may keep decoded
image data in PDFium's per page image cache, which for an A0 scan at 300 dpi could be 100 MiB or
more per page. Measure once the raster pipeline exists (M4); if it is large, cap the cache by an
estimated byte size or keep one page for raster sheets.

## Reproduce

```sh
./scripts/fetch-pdfium.sh                     # once; or set DIMO_PDFIUM_PATH
./scripts/perf.sh                             # about 2 minutes, writes target/perf/summary.{json,md}

# only the document
cargo run --release -p dimo-synth -- --stress --sheets 50 --out target/perf

# frame times in the app (debug build, window opens by itself, stop it with Ctrl+C)
DIMO_DEV_OPEN=$PWD/target/perf/stress_1_50.pdf DIMO_DEV_BALLOONS=500 DIMO_DEV_PAN_CHECK=1 \
  pnpm -C apps/desktop tauri dev
# add DIMO_DEV_SHEET=3 DIMO_DEV_VIEW=100@1700,1200 for the 100 percent view
```

The result line starts with `[dimo dev] pan frame times`. For the memory of the webview, sum the
resident size of `dimo-desktop` and its `WebKit` helper processes (macOS: Activity Monitor or
`ps -axo pid,rss,comm`; Windows: the `msedgewebview2` processes).
