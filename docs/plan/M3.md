# M3 Simple shop reports

Goal from [09 Roadmap](../spec/09-roadmap.md): samples, measurement grid, pass/fail, simple check
sheet and generic inspection report (PDF and XLSX), one bundled default template.

**Exit criterion:** a one person shop goes from customer PDF to a finished report in one sitting.
Measured with a timed manual procedure (`docs/perf/M3-exit.md`, written in T3.11, same form as
[M1-exit](../perf/M1-exit.md)): the owner takes a real drawing of his own with at least 25
inspected characteristics and three parts. Starting with Dimo open and no project, he balloons the
drawing, prints the check sheet, measures the parts (measuring time not counted), enters the
results and exports the inspection report as PDF and XLSX. The criterion is met when:

1. the whole run is done in Dimo without any other program (no spreadsheet, no PDF editor, no
   calculator for limits or pass/fail), in one session without restarting the app;
2. Dimo working time (clock paused while measuring) is at most 60 minutes for 25 characteristics
   and three parts;
3. the report has no error when checked against the drawing and the measured values (number,
   requirement, limits, value, verdict per cell, overall verdict, drawing revision and hash);
4. exporting the same project again gives byte identical PDF and XLSX files.

Requirements in scope: FR-MEA-01, FR-MEA-02, FR-MEA-03, FR-MEA-06, FR-EXP-04, FR-EXP-06,
FR-RVC-04, FR-EXP-11 (for the new outputs), FR-DOC-07 (hash shown on the report), FR-BAL-10 and
D-23 (issued reports lock numbering), D-30, D-32, NFR-UX-01 (keyboard entry), NFR-UX-05 (shape plus
color for pass/fail), NFR-UX-06, NFR-SEC-05 (sandboxed template rendering), NFR-REL-03 (schema
version 3 with migration), NFR-PERF-06 (report export as a cancellable background job).

Out of scope (later milestones or after 1.0):

- Result import from CSV and spreadsheets with mapping profiles (FR-MEA-04), custom templates,
  spreadsheet templates with placeholders, template preview, template packs, first article forms,
  initial sample report, customer profiles (FR-MEA-04, FR-EXP-02, FR-EXP-03, FR-EXP-05, FR-EXP-07,
  FR-EXP-08, FR-SET-01, FR-SET-02): M7.
- Template snapshots in the project container (`templates/`, spec 07, optional): with custom
  templates in M7. The bundled template is referenced by id and version.
- QIF results (FR-MEA-05, FR-EXP-10): M9. CLI report export (FR-AUT-01): M9.
- Review states and "export warns if unverified characteristics remain" (FR-REV-01, FR-REV-07):
  M4. Revision import and carry over of results (FR-RVC-01 to 03): M8.
- Statistics across samples (Cp, Cpk, charts): after 1.0. Sampling plans and decision rules with
  measurement uncertainty (ISO 14253-1): not planned; values are compared with the limits as
  entered (decision 3).
- Digital signatures, company logo on reports, Letter paper size.
- Demo drawing, getting started guide, installers, table verification: release 0.1.

Tasks are grouped in waves. Tasks in one wave can run in parallel. Each task ends with green
`./scripts/check.sh` and a signed commit. Tasks marked **plan mode** touch more than one crate or
add a dependency (CLAUDE.md).

## Decisions taken in this plan

The spec leaves these open. They are the simplest options consistent with it. The owner reviewed
the plan and confirmed decisions 1 to 17 and the 60 minute exit limit on 2026-10-12.

1. **Data model version 3.** `Project` gains `samples`, `results`, `report_info` and
   `issued_reports`; `Characteristic` gains `result_type`. `schema_version` 3 with a migration from
   2 (empty lists, default report info) and a fixture; JSON Schema regenerated.
   - `Sample`: `SampleId` (UUID newtype), `serial` (text), `date` (text `YYYY-MM-DD` or empty),
     `inspector`, `gauges` (free text), `comment`. Order of the list is the column order.
   - `MeasurementResult`: `sample`, `characteristic`, `value` (`variable` with a `Decimal`, or
     `attribute` with `ok` or `not_ok`), `source` (`manual`; `import` follows in M7), `comment`. At
     most one result per sample and characteristic. Stored sorted by sample order, then
     characteristic placement order, so saves stay byte identical.
   - `ReportInfo`: report number, report date (text `YYYY-MM-DD`), company name (the issuing shop),
     inspected by, approved by, remarks. All text, empty means not set.
   - `IssuedReport` (spec 07): report kind, template id and version, current revision id and drawing
     SHA-256, export time (from the `Environment` clock, project data only, never written into the
     file), output file SHA-256, file format.
   - New commands, each with an inverse: add samples, update sample, delete samples (with their
     results), move samples, set results (batch, one undo step for a paste), clear results, set
     result type, update report info, update revision label (no command sets
     `DrawingRevision.label` today), record issued report.
2. **The evaluation is computed, not stored.** Spec 07 says a result holds "the evaluation". A
   stored verdict goes stale when limits change (re-interpretation, hand edits). `dimo-core`
   computes the verdict from the result and the current limits whenever it is needed; reports
   print it, and an issued report keeps its output hash, so what was sent stays provable. The
   project file stores only what the user entered. Deviates from the wording of spec 07.
3. **Pass/fail rules (FR-MEA-03).**
   - Limits are inclusive: a value equal to a limit passes. Comparison is exact on `Decimal`, the
     entered value is never rounded. No measurement uncertainty in the decision.
   - Only an upper or only a lower limit (`MAX`, `MIN`, one sided): checked against that limit.
   - Variable result without any limit: verdict `not_evaluated`, shown with its own mark; it does
     not fail the part but keeps the overall verdict from being `pass`.
   - Attribute result: `ok` passes, `not_ok` fails, limits ignored.
   - Verdict per cell: `pass`, `fail`, `not_evaluated`, `missing` (no result). Per sample and for
     the report: `fail` if any cell fails, else `pass` if every inspected characteristic has a
     `pass` in that sample (all samples for the report), else `open`.
   - Limits from draft tables (D-43) evaluate normally; the grid and the report mark them as in the
     table today.
4. **Result type per characteristic (FR-MEA-06).** `result_type` is `auto`, `variable` or
   `attribute`. `auto` means variable if the characteristic has a limit, else attribute (threads,
   notes, surface texture without values, material requirements become go/no go or visual OK). The
   user can override per characteristic in the table and the detail panel. Changing the type is
   refused while results of the other type exist (clear them first, nothing is converted silently).
   Owner addition 2026-10-12: the first result set on an `auto` characteristic pins its type to
   the effective one (variable or attribute), so a later limit change never flips it. German shop
   notation `i.O.`/`io` and `n.i.O.`/`nio` is accepted for attribute results.
5. **What is measured.** The grid and the reports contain inspected characteristics only:
   `inspect = true` and status not `rejected`, in number order. Reference and basic dimensions
   (`inspect = false`, D-25) are left out of grid, check sheet and report. A characteristic with
   quantity `4X` and one balloon (D-22 default) gets one result per sample: the user enters the
   worst value. Shops that want one value per feature use the sub-number setting (D-22).
6. **Samples and serial ids (FR-MEA-01).** New projects have no samples. "Add samples" adds N
   (1 to 100 at once, default 1) with serials continuing the highest plain number (`1`, `2`, `3`),
   date empty, inspector prefilled with the audit user (D-27). Serials are free text, trimmed,
   non empty, unique within the project (case sensitive). Up to 500 samples per project; above that
   the command is refused.
7. **Measurement grid and keyboard flow (FR-MEA-02, NFR-UX-01).** Measure view (D-50): rows are
   characteristics (number, requirement text, nominal, limits, unit, result type), one column per
   sample, frozen left columns, virtualized like the characteristic table (TanStack). Typing in a
   cell starts editing. Enter commits and moves down (one part is measured top to bottom),
   Shift+Enter up, Tab right, Shift+Tab left, arrow keys move without editing, Delete clears,
   Escape cancels. Attribute cells: `o` or `+` sets OK, `n` or `x` sets not OK, Space toggles.
   Paste of a rectangular block of values from the clipboard sets results in one undo step. Every
   commit is a Rust command; Rust parses and validates the text, the frontend shows Rust's refusal.
  
8. **Units and decimals in the grid.** Values are entered in the characteristic's unit (mm, inch
   or decimal degrees), shown in the unit column; no conversion in the grid. Decimal point and
   decimal comma are accepted, the minus sign as hyphen or U+2212. The value keeps the scale typed
   (`12.10` stays `12.10`) and is shown and reported as typed. Degree-minute entry for angles is
   not in M3.
9. **Color coding (FR-MEA-03, D-24, NFR-UX-05).** Shape plus color, never color alone: pass is a
   check mark with the success token, fail is a cross with the danger token and a bold cell
   border, not evaluated is a hollow circle, missing is an empty cell. Same marks in the PDF report
   (printable in black and white) and as text plus fill in the XLSX report. Row and sample
   summaries show counts.
10. **Report template format and location (FR-EXP-06, D-30).** One bundled template set
    `dimo-default`, version 1, in `data/templates/dimo-default/`: `template.toml` (id, version,
    documents), `check-sheet.typ`, `inspection-report.typ`, a shared `common.typ` and the label
    texts in English and German (D-32) inside the template, so a later custom template (M7) owns
    its wording. Files are embedded at compile time. Rust passes one JSON data file with every
    value already formatted as text (numbers, dates, verdicts), so the template never computes
    with numbers (rule 5) and never decides pass or fail (rule 2). The data format is documented in
    `data/templates/README.md` with a JSON Schema, as the base for M7 custom templates.
11. **PDF reports with Typst (D-30, spec 06).** D-30 and spec 06 name Typst as a library, so the
    reports use it, not the pdfium-render page object writer (which has no text layout, tables or
    page breaks). Typst is a new dependency with a large crate tree, so T3.2 starts with a measured
    spike: crates added, licenses (`cargo deny`), release binary size, clean build time, render
    time, determinism, sandbox. If a number is unacceptable the agent stops and reports to the
    owner with the pdfium-render alternative; it does not switch silently (a switch needs a new
    ADR because D-30 is binding). The Typst `World` serves only the embedded template files, the
    data file and the bundled fonts: no file system, no network, no package downloads, no plugins
    (NFR-SEC-01, NFR-SEC-05). Fonts: Open Sans Regular is added next to the existing Bold (same
    version and license, provenance in `data/fonts/README.md`).
12. **Report layouts (FR-EXP-04, D-30, D-31).** Dimo's own neutral layouts, A4 landscape, derived
    from what an inspection record needs to show: that the part meets the drawing requirements,
    and who released it (ISO 9001 clause 8.6): what was inspected (part, drawing, revision, file
    hash), against which requirements (number, requirement text, nominal, limits, unit, rule
    marker, method and gauge), on which parts (sample serials, dates, inspectors, gauges), with
    which results and verdicts, and who inspected and approved it.
    - Header on every page: company name, document title, part number and name, customer, order
      reference, drawing file name, revision label, drawing SHA-256 (first 16 hex digits in the
      header, full value on the first page), report number and date, page x of y.
    - Check sheet: characteristic table with empty result columns for printing; one column per
      sample with serials printed if samples exist, otherwise a chosen number of blank columns
      (1 to 10, default 3).
    - Inspection report: summary block (overall verdict, counts of pass, fail, not evaluated,
      missing per sample), sample block, characteristic table with results and marks, remarks,
      signature block.
    - More samples than fit on a page (about 6 columns): the table repeats in blocks of columns,
      with the characteristic columns repeated. The table header repeats on every page.
13. **XLSX reports (D-30).** Built in code with `rust_xlsxwriter` (already a dependency), not from a
    template (spreadsheet templates are M7). Two workbooks with the same content as the PDFs: sheet
    "Report" with header block, table (one column per sample) and signature fields; values as
    number cells with the decimals typed (as the T1.4 list export), verdicts as text plus cell
    fill, print setup A4 landscape with repeated header rows. Fixed document properties and ZIP
    times as in T1.4.
14. **Determinism of reports (FR-EXP-11, rule 11).** The output depends only on the project, the
    export options, the template version and the app version. Dates in the files come from the
    project (`report_info.report_date`, else the project modification date), never from the
    clock; the PDF document id is derived from a hash of the data; fonts and the template are
    embedded in the binary. Tests assert byte identical output for two renders and snapshot the
    data JSON and the extracted PDF text.
15. **Signatures and approval.** No digital signatures. The signature block has two rows,
    "Inspected by" and "Approved by", each with name (from report info, prefilled with the audit
    user for the inspector), date and an empty signature field for a handwritten signature.
    Company name is entered once in the app settings and copied into the project's report info when
    it is empty, so the report depends on the project only.
16. **Limits change after results exist.** Results stay; the verdict is recomputed from the new
    limits (decision 2). The grid marks characteristics whose limits or result type changed after
    the last issued report with a hint marker (the issued report record holds the drawing hash and
    output hash; the audit log holds the old limits). Deleting a characteristic or a sample deletes
    its results in the same undoable command; the UI asks first when results exist.
17. **Issued reports (D-23, FR-BAL-10).** "Export as issued" works for the check sheet and the
    inspection report as for the other exports today: numbering locks in the same step, and an
    `IssuedReport` record is added after the file is written (one undoable step together with the
    lock). Draft tables (D-43) and open or missing results give a warning before an issued export,
    never a refusal.
